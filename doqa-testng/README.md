# Адаптер TestNG: `app.doqa:doqa-testng`

Адаптер передаёт результаты тестов TestNG в DoQA: через API DoQA или через файлы
Allure-совместимого формата, которые загружаются в DoQA отдельным шагом. Для каждого теста DoQA
получает исход, шаги, фикстуры, параметры, вложения и ссылки. По этим данным DoQA создаёт и
обновляет автотесты.

Ошибки отправки не останавливают тесты и не меняют результат сборки: адаптер пишет WARNING в лог и
продолжает работу.

Минимальная поддерживаемая версия — **TestNG 7.4**: адаптер не вызывает API, появившийся позже
(`ITestResult.id()`, `getParameterIndex()`, `upstreamDependencies()`). Собирается и тестируется
адаптер с TestNG 7.12. Требуется JDK 11 или новее. Для JUnit используйте
[`doqa-junit5`](../doqa-junit5/README.md) или [`doqa-junit4`](../doqa-junit4/README.md).

## Быстрый старт

**Шаг 1.** Добавьте зависимость. Это единственный обязательный шаг:

```xml
<dependency>
  <groupId>app.doqa</groupId>
  <artifactId>doqa-testng</artifactId>
  <version>0.1.5</version>
  <scope>test</scope>
</dependency>
```

```groovy
testImplementation("app.doqa:doqa-testng:0.1.5")   // Gradle
```

Все модули монорепозитория выпускаются с одной версией; актуальная указана в
[корневом README](../README.md).

**Шаг 2.** Запустите тесты.

Регистрировать listener не нужно. Адаптер указан в файле
`META-INF/services/org.testng.ITestNGListener`, и TestNG сам подключает отчётный listener и
интерцептор для выборочных прогонов. В JUnit 4, для сравнения, listener нужно указывать в surefire
или подключать рунером.

Если подключение к DoQA не настроено, адаптер записывает результаты в `./results/` в
Allure-совместимом формате. Эти файлы принимает конвейер загрузки DoQA, их также можно открыть в
Allure Report. Загрузить файлы в DoQA можно командой `doqactl upload` или отдельной джобой CI.
Аннотации не обязательны: каждый тест получает идентификатор автотеста автоматически.

**Шаг 3 (необязательно).** Чтобы отправлять результаты в DoQA через API, создайте `doqa.properties`
в рабочей директории запуска тестов (для Maven это каталог модуля) или задайте те же настройки
через переменные окружения или системные свойства JVM. Путь к файлу можно изменить свойством
`-Ddoqa.config=…`.

```properties
url=https://demo.doqa.app
token=<project token из настроек пространства>
spaceId=42
```

Когда заданы `url`, `token` и `spaceId`, адаптер создаёт прогон в DoQA и отправляет в него
результаты: по умолчанию одним пакетом в конце прогона, с `importRealtime=true` после завершения
каждого блока `<test>`.

> ⚠️ Если эти настройки лежат в `doqa.properties`, в DoQA отправляется каждый запуск тестов,
> включая локальные. Обычно локально файла с настройками нет и результаты записываются в файлы, а
> в CI настройки передаются через переменные окружения `DOQA_URL` / `DOQA_TOKEN` / `DOQA_SPACE_ID`.

## Регистрация

| Способ | Когда нужен |
|---|---|
| **зависимость `doqa-testng`** *(по умолчанию)* | всегда; файл SPI подхватывает любая среда, которая запускает `org.testng.TestNG`: surefire, Gradle (`test { useTestNG() }`), IDE, командная строка |
| `<listeners><listener class-name="app.doqa.testng.DoqaTestNgListener"/></listeners>` в `testng.xml` | если среда запуска отключила SPI или заменила `ITestNGListenerFactory` |
| surefire `<properties><property><name>listener</name><value>app.doqa.testng.DoqaTestNgListener</value></property></properties>` | то же для Maven |
| `@Listeners(DoqaTestNgListener.class)` на тестовом классе | если нужна явная привязка в коде |

Способы можно сочетать: TestNG подключает один listener каждого класса, поэтому отчёты не
дублируются. По этой же причине интерцептор выборочного прогона (`DoqaMethodInterceptor`) вынесен в
**отдельный** класс: интерцепторы TestNG не дедуплицирует, а ручная регистрация listener не должна
приводить к повторному отбору тестов.

Чтобы выключить адаптер, не удаляя зависимость, задайте `doqa.reporting=off`. Кроме того, TestNG
позволяет не подключать listener через SPI опцией командной строки
`-spilistenerstoskip app.doqa.testng.DoqaTestNgListener` (при программном запуске —
`TestNG.setListenersToSkipFromBeingWiredInViaServiceLoaders(...)`).

## Что адаптер передаёт без настройки

Флаги и изменения тестов не нужны: всё в таблице работает сразу после подключения зависимости.

| Данные | Откуда адаптер их берёт |
|---|---|
| Исход, сообщение, stack trace, длительность | исход из `ITestResult.getStatus()`, время из `getStartMillis()` и `getEndMillis()` самого TestNG |
| Шаги `Doqa.step` и `@Step` | все callbacks инвокации приходят в её поток, поэтому шаги тела попадают в блок `call` без дополнительной обработки |
| `@BeforeMethod` / `@AfterMethod` | отдельный узел на каждый вызов в блоках setup и teardown результата |
| `@BeforeGroups` / `@AfterGroups` | те же блоки setup и teardown теста, перед которым фикстура выполнилась |
| `@BeforeClass` / `@AfterClass` | фикстуры класса: узел на каждый метод, время измеряет TestNG (а не интервал между двумя событиями) |
| Шаги, вложения и сообщения **внутри** фикстур | на время фикстуры адаптер связывает контекст с её узлом, и всё, что добавлено внутри, попадает в этот узел |
| Реальные значения аргументов `@DataProvider` / `@Parameters` | `ITestResult.getParameters()` доступны listener, адаптер записывает их в `parameters[]` результата |
| Плейсхолдеры `{param}` в `@DoqaId`/`@DoqaTitle` и других аннотациях | из тех же значений; имена аргументов берутся из сигнатуры метода (нужен `-parameters`, см. ниже) |
| `groups` → теги автотеста | `ITestNGMethod.getGroups()`, включая группы, объявленные на классе |
| `@Test(description = "…")` | имя автотеста (если нет `@DoqaDisplayName`) |
| `@Test(enabled = false)` | `skipped` с причиной. TestNG не присылает событий по таким тестам, поэтому адаптер читает исключённые методы блока `<test>` |
| Пропуск из-за `dependsOnMethods`/`dependsOnGroups` или упавшей фикстуры | `skipped` со списком методов, из-за которых тест пропущен (`getSkipCausedBy`), и исходной ошибкой |
| Повтор (`@Test(retryAnalyzer = …)`) | отправляются **все** попытки; упавшая попытка получает `failed` или `broken`, а не `skipped` |
| Выборочный прогон (режим 0) | невыбранный тест **не выполняется** (см. ниже) |
| Порядок выполнения по плану DoQA | тот же интерцептор возвращает методы блока `<test>` в порядке плана |
| Realtime | результаты класса отправляются в конце его блока `<test>`, когда `@AfterClass` уже выполнен |
| Устойчивость к ошибкам | исключение из listener TestNG превращает в ошибку конфигурации, и прогон становится красным. Поэтому каждый callback адаптера перехватывает свои ошибки: ошибка отправки даёт только WARNING |

**Почему отправка отложена.** TestNG не сообщает о событиях после `@AfterMethod`: последний callback
`ITestListener` приходит **до** фикстур teardown. Поэтому этот callback только фиксирует исход, а
результат отправляется на первом событии, которое показывает, что teardown завершён: следующая
инвокация или следующая фикстура before в том же потоке, конец класса, конец блока `<test>` или
конец прогона. Результат отправляется ровно один раз и не раньше `@AfterMethod`, поэтому шаги
teardown есть в отчёте.

## Способ отправки (`reporting`)

| `reporting=` | Поведение |
|---|---|
| `auto` *(по умолчанию)* | если заданы `url`, `token` и `spaceId`, результаты отправляются через API; иначе записываются в файлы, и адаптер пишет в лог WARNING со списком недостающих настроек |
| `api` | результаты отправляются только через API; без полного набора настроек адаптер пишет WARNING со списком недостающих настроек и отключается |
| `files` | результаты записываются в `resultsDir` (по умолчанию `results/`) |
| `off` | адаптер отключён |

В файловом режиме тестовому процессу не нужны ни доступ к DoQA, ни токен. Файлы загружает
следующий шаг пайплайна, например:

```yaml
# .gitlab-ci.yml
test:
  script: mvn test          # адаптер пишет results/
  artifacts:
    paths: [results/]

upload-to-doqa:
  needs: [test]
  script: doqactl upload --token "$DOQA_TOKEN" --space "$DOQA_SPACE_ID" results/
```

Если на старте DoQA отклонил запрос или не ответил (401 или 403 из-за токена, 422 при отсутствии
активной CI-привязки, сетевая ошибка), адаптер не отключается, а записывает результаты всего
прогона в `resultsDir` и пишет в лог WARNING с причиной и подсказкой. Если DoQA отклонил пакет
результатов посреди прогона (обрыв связи, отозванный токен), в файлы записывается только этот
пакет, остальные адаптер продолжает отправлять через API.

Рядом с результатами адаптер записывает `doqa-reporting.properties` (`sink=api|files`, `runId`,
`delivered`, `fallbackResults`). По этому файлу джоба загрузки отличает ситуацию «файлов нет,
потому что всё отправлено через API» от ситуации «адаптер не отработал» и загружает то, что
осталось на диске.

## Настройки

Источники по возрастанию приоритета: файл `doqa.properties`, переменные окружения `DOQA_*`,
системные свойства JVM `-Ddoqa.*`. Путь к файлу задаётся свойством `-Ddoqa.config=…` или
переменной `DOQA_CONFIG`.

| Ключ (`doqa.properties` / `-Ddoqa.<ключ>`) | Переменная окружения | Назначение | По умолчанию |
|---|---|---|---|
| `reporting` | `DOQA_REPORTING` | `api` / `files` / `auto` / `off` | `auto` |
| `resultsDir` | `DOQA_RESULTS_DIR` | каталог для файлов результатов | `results` |
| `url` | `DOQA_URL` | адрес DoQA | — |
| `token` | `DOQA_TOKEN` | токен проекта или персональный токен (другое имя переменной: `DOQA_PRIVATE_TOKEN`) | — |
| `spaceId` | `DOQA_SPACE_ID` | id пространства (другое имя переменной: `DOQA_PROJECT_ID`) | — |
| `configurationId` | `DOQA_CONFIGURATION_ID` | конфигурация прогона (браузер, ОС, окружение) | — |
| `testRunId` | `DOQA_TEST_RUN_ID` | существующий прогон (нужен для режимов 0 и 1) | — |
| `testRunName` | `DOQA_TEST_RUN_NAME` | имя создаваемого прогона (режим 2) | — |
| `adapterMode` | `DOQA_ADAPTER_MODE` | режим выбора прогона: `0`/`selective`, `1`/`existing`, `2`/`new` ([см. ниже](#режимы-прогона)) | `2` |
| `importRealtime` | `DOQA_IMPORT_REALTIME` | `true` — отправлять результаты по ходу прогона: пакет на каждый завершённый блок `<test>` вместе с `@AfterClass` его классов | `false` (один пакет в конце) |
| `certValidation` | `DOQA_CERT_VALIDATION` | `false` — не проверять TLS-сертификат и имя хоста (для самоподписанных сертификатов) | `true` |
| `proxy` | `DOQA_PROXY` | HTTP-прокси, `host:port` | — |
| `environment` | `DOQA_ENVIRONMENT` | метка окружения прогона (матрица окружений DoQA) | — |
| `pipelineId` | `DOQA_PIPELINE_ID` | пайплайн CI, к которому привязывается прогон | `CI_PIPELINE_ID` / `GITHUB_RUN_ID` |
| `ciRunId` | `DOQA_CI_RUN_ID` | id запуска CI, который инициировал DoQA; DoQA передаёт его в пайплайн, адаптер возвращает с результатами | — |
| `branch` | `DOQA_BRANCH` | ветка прогона | `CI_COMMIT_REF_NAME` / `GITHUB_REF_NAME` |
| `batchSize` | `DOQA_BATCH_SIZE` | максимальное число результатов в одном запросе | `100` |
| `requestTimeoutMs` | `DOQA_REQUEST_TIMEOUT_MS` | таймаут HTTP-запроса, мс | `30000` |
| `retries` | `DOQA_RETRIES` | общее число попыток на запрос (повторяются только запросы, которые безопасно повторить) | `3` |
| `retryBackoffMs` | `DOQA_RETRY_BACKOFF_MS` | пауза перед второй попыткой, мс; перед каждой следующей удваивается | `500` |
| `maxTraceLength` | `DOQA_MAX_TRACE_LENGTH` | максимальная длина stack trace в результате, символов | `100000` |
| `maxMessageLength` | `DOQA_MAX_MESSAGE_LENGTH` | максимальная длина сообщения, символов | `10000` |
| `maxParameterLength` | `DOQA_MAX_PARAMETER_LENGTH` | максимальная длина значения параметра, символов | `2000` |

Подробности разбора настроек (алиасы, пустые значения, повторы запросов) описаны в
[README `doqa-client`](../doqa-client/README.md#настройки).

### Режимы прогона

**Режим 2 (`new`, по умолчанию).** Адаптер создаёт прогон и отправляет в него все результаты.
Подходит для CI, где выполняются все тесты.

**Режим 1 (`existing`).** Адаптер отправляет все результаты в существующий прогон `testRunId`,
созданный заранее в интерфейсе DoQA или через API. Если `testRunId` задан, а `adapterMode` нет,
адаптер работает в этом режиме, чтобы указанный прогон не был проигнорирован.

**Режим 0 (`selective`).** Адаптер запрашивает у DoQA список автотестов прогона `testRunId` и
выполняет только их. Этот режим DoQA включает, когда запускает выбранные автотесты в CI: он
передаёт в пайплайн `DOQA_TEST_RUN_ID` и `DOQA_ADAPTER_MODE=0`. Ограничения режима описаны в
разделе [Выборочный прогон](#выборочный-прогон-и-порядок-по-плану-doqa).

## Параллельное выполнение

Адаптер поддерживает параллельное выполнение TestNG без дополнительной настройки: `parallel="methods"`,
`parallel="classes"`, `parallel="tests"`, `threadPoolSize` у `@Test`, `@DataProvider(parallel = true)`.
TestNG выполняет инвокацию **вместе с её фикстурами в одном потоке** и присылает все её callbacks в
этом же потоке. Поэтому адаптер привязывает контекст шагов к потоку, а `@BeforeMethod` и
`@AfterMethod` попадают в результат своей инвокации.

Реестр открытых инвокаций потокобезопасен. При `parallel="tests"` завершившийся блок `<test>`
отправляет только свои классы и не может досрочно отправить инвокацию соседнего блока, у которой
ещё выполняется teardown.

## Выборочный прогон и порядок по плану DoQA

TestNG один раз для каждого блока `<test>` передаёт интерцептору все его тестовые методы (после
фильтрации по группам и `<methods><include>`, до выполнения первого класса) и выполняет тот
список, который интерцептор вернул. Адаптер возвращает только автотесты, выбранные в прогоне.
Невыбранные тесты не выполняются, не порождают ни одного события и не появляются как `skipped`.
При отправке адаптер ещё раз проверяет `externalId`: идентификаторы-шаблоны (`login_{browser}`) при
отборе сравниваются по маске, а при отправке — по фактическому значению.

Вне режима 0, а также если идентификатор не удалось определить, интерцептор возвращает исходный
список без изменений: ошибка адаптера не должна исключать тест из прогона.

> ⚠️ **Зависимости невыбранных тестов возвращаются в прогон.** Если выбранный тест объявляет
> `dependsOnMethods`/`dependsOnGroups` на тест, которого нет в прогоне, исключить зависимость
> нельзя: TestNG завершит с ошибкой весь блок `<test>` («… is depending on method …, which is not
> annotated with @Test or not included»), и прогон не даст результатов. Поэтому адаптер возвращает в
> прогон все транзитивные зависимости выбранных тестов. Эти методы **выполняются**, но их
> результаты **не отправляются**, и прогон содержит только выбранные автотесты. Время CI на
> зависимости тратится.

> ⚠️ **Граф зависимостей важнее плана.** TestNG учитывает `dependsOnMethods` **после**
> интерцептора, поэтому зависимость всегда выполняется раньше зависимого теста, какую бы позицию ей
> ни дал план. Порядок из интерцептора важнее `@Test(priority)`: TestNG использует возвращённый
> список.

**Порядок выполнения по плану.** Список автотестов в режиме 0 приходит из DoQA упорядоченным: это
порядок набора запуска, который задают в интерфейсе DoQA перетаскиванием. Интерцептор возвращает
методы в этом порядке; тесты, которых нет в плане, идут в конце в исходном порядке. Сортировка не
меняет состав прогона. Ограничения: порядок применяется только в режиме 0 и только внутри одного
блока `<test>` (TestNG может дополнительно сгруппировать методы по экземплярам классов), а также
действуют ограничения графа зависимостей, описанные выше.

> ⚠️ Если прогон выбрал автотесты, но ни один из них не совпал с найденными тестами, адаптер пишет
> в лог WARNING со списком выбранных `externalId`. Обычно причина в том, что метод переименован
> или класс перенесён. Отправьте в DoQA результаты полного прогона, чтобы каталог автотестов
> получил актуальные идентификаторы.

## Разметка тестов

Разметка необязательна. Аннотации `@Doqa*` и фасад `app.doqa.Doqa` те же, что в JUnit-адаптерах: они
находятся в общем модуле `doqa-java-commons`, поэтому при смене фреймворка импорты менять не нужно.

```java
@DoqaLabels({"regression"})                     // класс-уровень: наследуется всеми тестами
public class LoginTests {

    @Test(groups = {"smoke"}, description = "Проверяет happy-path входа по паролю")
    @DoqaId("LOGIN-1")                          // стабильный ключ автотеста (рекомендуем)
    @DoqaTitle("Успешный вход")
    @DoqaDescription("Проверяет happy-path входа по паролю")
    @DoqaDisplayName("Вход по паролю")          // имя автотеста (иначе - description / имя метода)
    @DoqaLabels({"smoke"})                      // объединится с класс-уровнем
    @DoqaTags({"ui"})                           // сложатся с нативными groups
    @DoqaLinks({@DoqaLink(url = "https://tracker/BUG-77", type = "defect", title = "флак на CI")})
    @DoqaCaseIds({1041})                        // привязка к ручным кейсам DoQA (N штук)
    @DoqaCreateManualCase                       // завести связанный ручной кейс для этого автотеста
    public void loginHappyPath() { … }
}
```

Ещё две аннотации задают место теста в дереве DoQA: `@DoqaNamespace` (по умолчанию пакет) и
`@DoqaClassName` (по умолчанию простое имя класса). Все аннотации `@Doqa*` работают и на уровне
класса и наследуются подклассами. Для скалярных значений аннотация метода важнее аннотации класса;
метки, теги и ссылки объединяются.

`@DoqaCreateManualCase` запрашивает создание ручного тест-кейса для автотеста, у которого нет
привязки к кейсам. Аннотация без параметров работает на методе и на классе. Кейс создаётся
независимо от того, включено ли такое создание в настройках пространства DoQA. Тот же запрос можно
сделать из тела теста вызовом `Doqa.addCreateManualCase()`. Аннотация и вызов дополняют друг друга,
выключить создание для отдельного теста нельзя. Кейс создаётся, когда DoQA получает результат; для
автотестов, которые уже есть в DoQA без кейсов, кейсы задним числом не создаются.

### Идентификатор автотеста

Если `@DoqaId` нет, адаптер берёт идентификатор из имени теста (`[DOQA-123]` или `@DOQA:123`; имя —
это `@Test(description)`, а без него имя метода), затем из Allure `@AllureId` (адаптер читает её без
зависимости от Allure), иначе вычисляет хэш от сигнатуры метода и описания теста. Хэш не меняется
между запусками, пока не изменились пакет, класс, метод, типы его параметров или описание; после
их изменения DoQA создаёт новый автотест. Явный `@DoqaId` сохраняет историю при любых
переименованиях.

### Аннотации TestNG

Дублировать уже существующую разметку не нужно, адаптер читает её сам:

| Что в тесте | Что в DoQA |
|---|---|
| `@Test(groups = {"smoke", "api"})` на методе и/или на классе | теги автотеста `smoke`, `api` (группы метода и класса объединяются) |
| `@Test(description = "…")` | имя автотеста; `[DOQA-123]` в описании используется как идентификатор |
| `@Test(testName = "…")` / `ITest#getTestName()` | имя конкретной инвокации в отчёте; в идентификатор **не** входит, поэтому историю не разделяет |
| `@Test(enabled = false)` | `skipped` с причиной `disabled with @Test(enabled = false)` |
| `@Test(dependsOnMethods = …)` / `dependsOnGroups` | `skipped` со списком методов, которые не прошли |
| `@Test(retryAnalyzer = …)` | каждая попытка — отдельный результат, все попытки относятся к одному автотесту |
| `@DataProvider`, `@Parameters` из `testng.xml`, `@Factory` | параметры результата (фактические значения аргументов метода) |

### Параметризованные тесты

TestNG передаёт значения аргументов listener, поэтому `parameters[]` и подстановка `{param}`
работают без дополнительной настройки:

```java
public class LoginTest {

    @DataProvider(name = "browsers")
    public Object[][] browsers() {
        return new Object[][]{{"chrome"}, {"firefox"}};
    }

    @Test(dataProvider = "browsers")
    @DoqaId("LOGIN-IN-{browser}")                // → LOGIN-IN-chrome, LOGIN-IN-firefox
    @DoqaTitle("Вход в {browser}")
    public void loginIn(String browser) { … }    // parameters: [{name: "browser", value: "chrome"}]
}
```

Имена параметров берутся из сигнатуры метода, поэтому проект стоит компилировать с флагом
`-parameters` (в maven-compiler-plugin это `<configuration><parameters>true</parameters></configuration>`).
Иначе параметры будут называться `arg0..argN`, а `{param}` по имени не раскроется.

Без плейсхолдера все инвокации одного метода объединяются в **один** автотест, а аргументы
передаются в `parameters[]`. Это относится к `@DataProvider`, `invocationCount` и экземплярам
`@Factory`. Аргументы, которые TestNG подставляет сам (`ITestContext`, `ITestResult`, `XmlTest`,
`Method`), в параметры не попадают.

### Runtime API

Вызовы из тела теста:

```java
import app.doqa.Doqa;
import app.doqa.Labels;
import app.doqa.client.LinkType;                          // типы ссылок приходят из doqa-client

Doqa.step("открыть страницу", () -> page.open());          // шаг (вложенные - просто вкладывайте)
int sum = Doqa.step("посчитать", () -> a + b);             // шаг со значением
Doqa.step("чекпоинт пройден");                             // мгновенный passed-шаг без тела
Doqa.step("создать заказ", "POST /orders", () -> …);       // шаг с description
Doqa.addParameter("env", "staging");
Doqa.addAttachments("target/screenshot.png");              // файл к тесту или открытому шагу
Doqa.addAttachment("response.json", bytes, "application/json"); // вложение из памяти, без temp-файла
Doqa.addAttachment("app.log", logText);                    // текстовое вложение (text/plain)
Doqa.addLink("https://jira/TASK-5", LinkType.REQUIREMENT);
Doqa.addLink(url, type, title, description);               // расширенная форма; есть и addLinks(Link...)
Doqa.addMessage("покупатель создан через фабрику");
Doqa.addCaseIds(1042);
Doqa.addCreateManualCase();                                // завести связанный ручной кейс
Doqa.addExternalId("CART-DYN-1");                          // стабильный id, заданный в рантайме
Doqa.addTitle("…"); Doqa.addDescription("…"); Doqa.addDisplayName("…");
Doqa.addLabels("…"); Doqa.addTags("…");
Doqa.addLabel(Labels.SEVERITY, "critical");                // key:value-метки (severity/owner/epic/…)
```

Вне выполняющегося теста или при `reporting=off` вызовы ничего не делают. Внутри фикстур они тоже
работают: данные попадают в узел этой фикстуры.

Шаги и вложения из потоков, которые создаёт тест (асинхронный код, собственные executor'ы), нужно
явно связать с контекстом теста:

```java
Doqa.Context ctx = Doqa.captureContext();
executor.submit(() -> Doqa.runWith(ctx, () -> Doqa.step("проверка из воркера")));
```

## Шаги `@Step` через AspectJ

Для фикстур и параметров в TestNG ничего включать не нужно. Аннотации `@Step` нужен аспект, который
агент AspectJ применяет при загрузке классов в тестовую JVM.

```java
@Step("авторизоваться под {user}")  // {param}-плейсхолдеры из аргументов метода; без текста - имя метода
void authorize(String user) { … }
```

```xml
<!-- агент должен быть зависимостью вашего проекта: адаптер его не приносит транзитивно -->
<dependency>
  <groupId>org.aspectj</groupId>
  <artifactId>aspectjweaver</artifactId>
  <version>1.9.24</version>
  <scope>test</scope>
</dependency>
```

```xml
<!-- пишет путь к джарнику агента в property ${org.aspectj:aspectjweaver:jar} -->
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-dependency-plugin</artifactId>
  <executions><execution><phase>initialize</phase><goals><goal>properties</goal></goals></execution></executions>
</plugin>
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-surefire-plugin</artifactId>
  <configuration>
    <argLine>-javaagent:${org.aspectj:aspectjweaver:jar} --add-opens java.base/java.lang=ALL-UNNAMED</argLine>
  </configuration>
</plugin>
```

Для Gradle:

```groovy
configurations { doqaAgent }
dependencies { doqaAgent "org.aspectj:aspectjweaver:1.9.24" }
test {
    useTestNG()
    jvmArgs "-javaagent:${configurations.doqaAgent.singleFile}",
            "--add-opens", "java.base/java.lang=ALL-UNNAMED"
}
```

Если агент подключать не нужно, используйте `Doqa.step("…", () -> …)`: он работает без агента.

> Версия `aspectjweaver` ограничивает версию байткода, с которой работает агент. Для новых JDK
> используйте актуальную версию `aspectjweaver` (1.9.24 работает с JDK до 24 включительно).

## Исходы

Адаптер определяет исход **только** по статусу `ITestResult`, а не по наличию исключения: у
успешного `@Test(expectedExceptions)` исключение в результате есть, а упавшая попытка с повтором
приходит со статусом пропуска.

| Что произошло | Исход в DoQA |
|---|---|
| `SUCCESS` (в том числе совпавший `@Test(expectedExceptions)`) | `passed` |
| `FAILURE` с `AssertionError` (`org.testng.Assert`, `SoftAssert.assertAll()`, AssertJ, opentest4j) | `failed` |
| `FAILURE` с любым другим исключением (NPE, ошибка инфраструктуры, таймаут `@Test(timeOut = …)`) | `broken` |
| `SKIP`: `SkipException`, пропуск из-за `dependsOnMethods`/`dependsOnGroups` или упавшей фикстуры | `skipped`; в сообщении причина и список методов из `getSkipCausedBy()` |
| Упавшая попытка с повтором (`SKIP` и `wasRetried()`) | `failed` или `broken` по исключению, **не** `skipped` |
| `SUCCESS_PERCENTAGE_FAILURE` | `failed` или `broken` по исключению: инвокация упала, а «в пределах процента» — это оценка метода, а не инвокации |
| `@Test(expectedExceptions)`, если исключение не совпало | TestNG выбрасывает `org.testng.TestException`, это не `AssertionError`, поэтому `broken` |
| `@Test(enabled = false)` | `skipped` |

DoQA по-разному обрабатывает `failed` и `broken` при кластеризации ошибок и анализе нестабильных
тестов.

## Ограничения

Что адаптер не делает или делает не полностью:

- **Фикстуры уровня `<suite>` и `<test>`** (`@BeforeSuite`, `@AfterSuite`, `@BeforeTest`,
  `@AfterTest`) **не прикрепляются к результатам**: в модели DoQA нет такого уровня. Они
  выполняются с пустым контекстом: шаги и вложения внутри них в отчёт не попадают, но и не
  попадают в чужой тест, который выполнится в этом потоке следующим.
- **Минимум TestNG 7.4.** Адаптер не вызывает `ITestResult.id()`, `getParameterIndex()`,
  `upstreamDependencies()` и другой API новее 7.4; собирается и тестируется с 7.12. На версиях ниже
  7.4 работа не гарантируется.
- **Экземпляры `@Factory` и `invocationCount` объединяются в один автотест**: сигнатура метода у них
  одна, а экземпляр в идентификатор не входит. Инвокации записываются в автотест как попытки.
  Различить их можно по параметрам результата: аргументы `@DataProvider` попадают туда сами, а
  параметры фабрики адаптер не читает, их нужно задать вручную
  (`Doqa.addParameter("browser", browser)`).
- **Фикстуры класса записываются один раз на класс за прогон.** Класс, который встречается в
  нескольких блоках `<test>`, и `@Factory` с несколькими экземплярами проходят полный цикл несколько
  раз; в отчёте останется первый набор узлов `@BeforeClass`/`@AfterClass`, иначе они бы
  повторялись у каждого теста класса.
- **`@BeforeGroups` выполняется один раз на группу**, поэтому его узел попадает в блок setup
  первого теста группы, а не всех её тестов.
- **Параметры `testng.xml`, которые не переданы в аргументы метода, в результат не попадают**, а
  имена аргументов берутся из сигнатуры метода, а не из `@Parameters`. `@CustomAttribute` адаптер не
  читает: для метаданных есть `@DoqaLabels`, `@DoqaTags` и `groups`.
- **Режим realtime отправляет результаты по блокам `<test>`**, а не по классам:
  `IClassListener.onAfterClass` в TestNG вызывается **до** `@AfterClass`, и отправка из него
  потеряла бы teardown класса. Под surefire без `testng.xml` весь прогон — один блок `<test>`,
  поэтому в режиме realtime результаты уйдут одним пакетом в конце. Чтобы отправлять частями,
  разбейте прогон на несколько блоков `<test>` в `testng.xml`.
- **Порядок по плану** работает только в режиме 0, только внутри блока `<test>` и только если его
  допускает граф `dependsOn*` (см. [Выборочный прогон](#выборочный-прогон-и-порядок-по-плану-doqa)).
- **Несколько форков создают несколько прогонов.** При `forkCount>1` или `reuseForks=false` каждый
  форк работает в своей JVM, и в режиме 2 каждый создаёт свой прогон. Задайте `testRunId` и
  `adapterMode=1` (или режим 0), тогда все форки пишут в один прогон.
- **Не подключайте `doqa-testng` и другой адаптер DoQA к одному прогону**: общая часть адаптеров
  хранит один фреймворк на JVM, и адаптеры перезапишут его друг у друга.
- **Переход между фреймворками без явного `@DoqaId` начинает историю автотеста заново**:
  вычисляемый идентификатор содержит префикс фреймворка (`testng:<hash>`, `junit5:<hash>`,
  `junit4:<hash>`). Чтобы сохранить историю, задайте `@DoqaId` до перехода.
- **`@Test(description)` входит в вычисляемый идентификатор.** У теста без `@DoqaId` описание
  участвует в хэше (и служит именем автотеста), поэтому изменение описания начинает историю заново.
  К параметризованным тестам это не относится: у них имя в хэш не входит.

## Устранение неполадок

| Симптом | Причина и решение |
|---|---|
| Результатов нет, в логе нет ни одной строки от DoQA | адаптер не участвует в прогоне: зависимость не в test scope, задан `doqa.reporting=off` или среда запуска отключила SPI (`-spilistenerstoskip`, свой `ITestNGListenerFactory`). В последнем случае укажите listener в `testng.xml` (см. [Регистрация](#регистрация)) |
| `Tests run: 0` или часть тестов не запустилась при успешной сборке | в test classpath есть и TestNG, и JUnit Platform: surefire выбирает **один** провайдер, и тесты второго фреймворка не запускаются. Уберите лишний фреймворк или укажите провайдер явно (`surefire-testng` в `<dependencies>` плагина) |
| Результаты в `results/`, а ожидались в DoQA | режим `auto` без настроек API, в логе есть WARNING «no reporting configuration found (missing …)». Задайте `url`, `token` и `spaceId`. Если файловый режим нужен, задайте `reporting=files`, и предупреждение пропадёт |
| DoQA недоступен или отклонил токен, в `results/` появились файлы | адаптер перешёл в файловый режим (в логе WARNING «could not establish the test run» или «results chunk failed»). Загрузите `results/` джобой загрузки, как в файловом режиме |
| `NoSuchMethodError: DoqaStepAspect.aspectOf()` | собственный `aop.xml` исключил аспект из области применения; добавьте `<include within="app.doqa.aspects.DoqaStepAspect"/>` |
| Шаги `@Step` не появляются | не подключён `-javaagent:aspectjweaver` (см. [Шаги `@Step` через AspectJ](#шаги-step-через-aspectj)); `Doqa.step(...)` работает и без агента |
| На JDK 16+ агент падает или шагов нет | добавьте `--add-opens java.base/java.lang=ALL-UNNAMED` в argLine |
| Параметры называются `arg0`, `arg1` | включите флаг компилятора `-parameters`: имена аргументов адаптер берёт из сигнатуры метода |
| `{param}` в `@DoqaId` или `@DoqaTitle` не раскрылся | имя в плейсхолдере не совпало с именем аргумента (часто это те же `arg0` без `-parameters`) или у инвокации нет аргументов (`invocationCount`, `@Factory`). Задайте значение сами: `Doqa.addParameter(...)` / `Doqa.addExternalId(...)` |
| В выборочном прогоне выполняются невыбранные тесты | это зависимости выбранных тестов: без них TestNG завершил бы блок `<test>` с ошибкой. Их результаты в прогон не отправляются. Чтобы не тратить на них время, уберите `dependsOnMethods` между выбранными и невыбранными тестами |
| Выборочный прогон упал с ошибкой «… is depending on method …, which is not annotated with @Test or not included» | адаптер не вернул в прогон все зависимости. Это ошибка адаптера, напишите в поддержку support@doqa.app. Проверьте значения `dependsOnMethods`/`dependsOnGroups` (TestNG считает их регулярными выражениями) у выбранных методов. Временное решение: `adapterMode=1` (прогон без отбора) или `@Test(ignoreMissingDependencies = true)` |
| Выборочный прогон ничего не выполнил, в логе WARNING со списком `externalId` | идентификаторы в DoQA и в коде разошлись (переименование или перенос); отправьте результаты полного прогона, чтобы каталог получил актуальные идентификаторы |
| Один запуск создал несколько прогонов в DoQA | `forkCount>1` или `reuseForks=false`: задайте `testRunId` и `adapterMode=1` |
| Локальные запуски создают прогоны в DoQA | уберите токен из локальной конфигурации или задайте локально `reporting=files` |
| Самоподписанный сертификат | `certValidation=false` (только для тестовых стендов) |
| В отчёте нет шагов из `@BeforeSuite`/`@BeforeTest` | так задумано: у этих фикстур нет уровня в модели DoQA (см. [Ограничения](#ограничения)). Перенесите нужные шаги в `@BeforeClass` или `@BeforeMethod` |
| Нужно выключить адаптер для одного прогона | `-Ddoqa.reporting=off` или опция TestNG `-spilistenerstoskip app.doqa.testng.DoqaTestNgListener` |

## Переход с Allure

- **Адаптер читает разметку Allure без зависимости от Allure:** `@AllureId` (идентификатор
  `ALLURE-<id>`), `@Epic`, `@Feature`, `@Story`, `@Owner`, `@Severity` (метки `key:value`), `@Link`,
  а также `@Issue` и `@TmsLink` со значением-URL (ссылки с типом), `@Description`. `@AllureId` также
  связывает автотест с ручным тест-кейсом DoQA с этим id: в файловом режиме через метку `AS_ID`,
  при отправке через API напрямую. Поэтому привязка к кейсам сохраняется без правок. Файловый режим
  записывает Allure-совместимые результаты с меткой `framework: testng`, поэтому существующий
  пайплайн загрузки продолжит работать.
- `allure-testng` подключается тем же механизмом SPI, поэтому при переходе нужно заменить только
  зависимость: `testng.xml` и настройки surefire менять не нужно.

## Сборка из исходников

Адаптер находится в монорепозитории `doqa-java` вместе с модулями `doqa-java-commons` и
`doqa-client`. Maven собирает их из корня одной командой и сам определяет порядок модулей:

```bash
mvn clean verify        # либо точечно: mvn -pl doqa-testng -am clean verify
```
