# doqa-java-commons: общая часть JVM-адаптеров DoQA

`app.doqa:doqa-java-commons` содержит код JVM-адаптеров DoQA, который не зависит от тестового
фреймворка. Модуль находится между адаптером конкретного фреймворка и API-клиентом:

```
ваши тесты ──► doqa-junit5 (обвязка фреймворка) ──► doqa-java-commons (этот модуль) ──► doqa-client (HTTP/файлы)
```

В модуле находится всё, что использует код тестов: фасад `Doqa` и аннотации `@Doqa*`. Поэтому при
смене тестового фреймворка импорты в тестах менять не нужно. Здесь же находится то, что нужно
автору адаптера: дерево шагов, вычисление идентификатора, сборка результата и сессия отправки.
Адаптер конкретного фреймворка связывает события фреймворка с этими компонентами.

**Зависимости:** `app.doqa:doqa-client` (у него самого внешних зависимостей нет) и
`org.aspectj:aspectjrt` (runtime для аспекта `@Step`). Классы Allure, JUnit и Jackson модуль в
classpath проекта не добавляет.

## Требования

- JDK 11 или новее.

## Установка

Тестовым проектам этот артефакт напрямую **не** нужен: подключите адаптер своего фреймворка
(например, `app.doqa:doqa-junit5`), он добавит модуль транзитивно. Прямая зависимость нужна только
для разработки нового адаптера:

```xml
<dependency>
    <groupId>app.doqa</groupId>
    <artifactId>doqa-java-commons</artifactId>
    <version>0.1.1</version>
</dependency>
```

## Состав

### Пользовательский API (одинаков во всех JVM-адаптерах)

- **`app.doqa.Doqa`** — фасад для кода теста:
  - `step(...)`: вложенные шаги с замером времени, шаг с возвращаемым значением, шаг-отметка без
    тела, шаг с описанием;
  - `addAttachments` / `addAttachment`: вложения из файлов или из памяти (байты или текст);
  - `addParameter`, `addLink(s)`, `addMessage`, `addLabels` / `addLabel` / `addTags`,
    `addCaseIds`;
  - `addCreateManualCase`: запрос на создание связанного ручного кейса в DoQA;
  - `addTitle` / `addDescription` / `addDisplayName`;
  - `addExternalId`: идентификатор автотеста для динамических тестов;
  - `captureContext()` / `runWith(...)`: перенос контекста теста в потоки, которые создал тест.

  Вне выполняющегося теста вызовы ничего не делают.
- **`app.doqa.annotations`** — аннотации разметки: `@DoqaId`, `@DoqaCaseIds`,
  `@DoqaCreateManualCase`, `@DoqaTitle`, `@DoqaDescription`, `@DoqaDisplayName`, `@DoqaLabels`,
  `@DoqaTags`, `@DoqaLink(s)`, `@DoqaNamespace`, `@DoqaClassName`, а также `@Step` для шагов.
  Плейсхолдеры `{param}` в названии шага заменяются значениями аргументов метода.
- **`app.doqa.Labels`** — ключи меток в формате `key:value`: `severity`, `owner`, `epic`, `feature`,
  `story`, `component`.
- **`app.doqa.aspects.DoqaStepAspect`** и файл `META-INF/aop.xml` в составе модуля — аспект
  AspectJ, который превращает методы с `@Step` в шаги отчёта. Аспект применяется агентом AspectJ при
  загрузке классов (`-javaagent:aspectjweaver.jar`) или при сборке. Точные настройки приведены в
  README адаптера. Если вы ограничиваете область применения аспектов через `<include>`, оставьте в
  ней `<include within="app.doqa.aspects.DoqaStepAspect"/>`: сам аспект должен входить в эту
  область.

### Внутренний API для адаптеров (`app.doqa.core`)

Классы этого пакета публичны для авторов адаптеров и не предназначены для кода тестов.

- **`DoqaSession`** — одна на процесс сессия отправки поверх `doqa-client`. Она выбирает способ
  отправки (`api`, `files`, `auto`, `off`) и управляет отправкой:
  - в пакетном режиме накапливает результаты до конца прогона и отправляет пакетами по
    `batchSize`; если DoQA отклонил пакет, в файлы записывается только этот пакет;
  - в режиме realtime отправляет результаты каждого класса верхнего уровня после того, как
    завершился его контейнер, включая `@AfterAll`;
  - в файловом режиме сразу записывает Allure-совместимые результаты.

  При каждой отправке сессия передаёт одно определение на `externalId`, предупреждает, если один
  `externalId` используют разные тестовые методы, и при завершении JVM отправляет или записывает то, что
  осталось в буфере.
- **`DoqaContexts` / `RuntimeContext` / `StepNode` / `Steps`** — реестр контекстов тестов (ключ —
  уникальный id теста во фреймворке; дополнительно хранится thread-local ссылка на текущий
  контекст), собранные данные теста и стек шагов. После удаления контекст закрывается: записи,
  которые приходят в него позже из других потоков, отбрасываются и не меняют уже отправленный
  тест.
- **`Attribution` / `SignatureHash`** — вычисление `externalId`: `@DoqaId`, затем `[DOQA-123]` или
  `@DOQA:123` в отображаемом имени, затем Allure `@AllureId` (читается через reflection), затем хэш
  сигнатуры `<framework>:<sha1>`.
- **`MetaReader` / `AllureCompat`** — чтение метаданных из аннотаций, включая аннотации Allure
  (`@Epic`, `@Feature`, `@Story`, `@Owner`, `@Severity` превращаются в метки `key:value`, `@Link`,
  `@Issue`, `@TmsLink` — в ссылки с типом). Аннотации `@Doqa*` имеют приоритет.
- **`ResultBuilder`** — превращает завершённый тест в `AutotestDef` и `AutotestResult`: раскладывает
  шаги по фазам, добавляет параметры, загружает вложения (вложения общих фикстур класса
  загружаются один раз), подставляет плейсхолдеры `{param}` и обрезает сообщения, stack trace и
  параметры до настроенных лимитов. В режиме 0 тест вне выборки ничего не загружает.
- **`ClassFixtures`** — фикстуры уровня класса (`@BeforeAll`/`@AfterAll`) с ключом по классу, в
  котором они объявлены, и поиском по цепочке вложенных классов.
- **`PlanSelection`** — выборочный запуск (режим 0) без типов конкретного фреймворка: входит ли
  тест в прогон (`active`, `allows`) и какое у него место в плане (`planIndex`). Если выборку не
  удалось определить, тест остаётся в прогоне, а порядок не меняется.
- **`Placeholders`**, **`Outcomes`**, **`AttachmentRef`**, **`TestRef`**, **`Limits`** —
  вспомогательные классы: подстановка плейсхолдеров с кэшем шаблонов, выбор исхода `failed` или
  `broken` и форматирование stack trace, описание вложения, координаты теста без типов
  фреймворка, обрезка строк.

## Как написать адаптер

Адаптер фреймворка отвечает за четыре задачи.

1. **Имя фреймворка.** Вызовите `AdapterRuntime.configure("<framework>", "<framework label>")` в
   статическом инициализаторе каждой точки входа (listener, фильтр discovery и т. п.). Первый
   аргумент становится префиксом вычисляемого `externalId`, второй записывается в результаты
   файлового режима.
2. **Жизненный цикл теста.** При старте теста вызовите `DoqaContexts.open(uniqueId)` и заполните
   `RuntimeContext.testRef`. Создавайте `TestRef` в одной фабрике на адаптер, чтобы discovery,
   сортировка и отправка вычисляли одинаковые идентификаторы, в том числе одинаковый признак
   параметризованного теста. Привяжите контекст (`bind`) к потоку, который выполняет тест. При
   завершении теста вызовите `DoqaContexts.remove(...)`, соберите результат через
   `ResultBuilder.build(ctx, outcome, message, traces, session.uploader(), session::allowsId,
   session.config)` и передайте его в `session.report(built)`.
3. **Точки отправки.** Вызывайте `session.flushClass(fqcn)` при завершении контейнера класса
   верхнего уровня и `session.flush()` в конце прогона. Класс верхнего уровня определяйте через
   `DoqaSession.topLevelClass(fqcn)`: по этому же ключу сессия хранит буферы. Ошибки отправки не
   должны прерывать сборку.
4. **Отбор и порядок (необязательно).** Если фреймворк позволяет вмешаться в discovery,
   используйте `PlanSelection.active()` и `allows(ref)` для исключения тестов,
   `PlanSelection.planIndex(ref)` как ключ стабильной сортировки и `PlanSelection.reset()` в конце
   прогона.

По этой схеме реализован адаптер `app.doqa:doqa-junit5`.

## Настройки

Настройки (подключение, выбор прогона, параметры отправки, лимиты длины) разбирает `doqa-client`,
а описаны они в README адаптеров. Модуль получает уже готовый `DoqaConfig`.

## Сборка

Модуль находится в монорепозитории `doqa-java` и собирается из его корня. Maven сначала соберёт
`doqa-client`:

```bash
mvn clean verify
```

Тесты проверяют вычисление идентификатора, поддержку аннотаций Allure, шаги и обрезку строк.
Доступ в сеть и запуск тестового фреймворка для них не нужны.
